# 健康 V1 存储与恢复方案（已批准 B）

日期：2026-10-26。依据当前原生HTML/CSS/JS、Hash+History及严格v1–v9备份实现。AGENTS.md要求新增存储结构先审阅兼容方案；既有八个localStorage键和妙想IndexedDB保持原样，无历史迁移。

用户决定：2026-10-26明确回复“批准 B：独立健康存储并新增完整 v10”。正式范围为下述独立健康模型、健康JSON与整站v10；原v5–v9兼容导出保留。以下推荐A文字保留为提案背景，实施状态以STATUS及架构为准。

## 推荐 A：独立健康键及健康 JSON

- 新增可选localStorage键`my-life-dashboard-health-v1`，内容`{version:1,records:[],lastImportAt:null}`。无数据只读为空，不启动写入或初始化演示内容；单次手动保存、确认导入、确认删除才写此键。使用原app的快照检查及写入回滚；不写其他模块键。
- 健康独立文件`{format:"lifeos-health-backup",schemaVersion:1,exportedAt,health}`。健康页提供导出/导入，原数据备份页增加明确的健康备份入口，说明原完整v9不含健康。原v5–v9格式、导入器、生活记录与公式保持；不擅自将健康字段塞进严格v9。
- 每条记录固定字段：`id,metric,value,unit,measuredAt,source,recordType,ingestedAt,updatedAt,periodStart,periodEnd,stages,externalId`。`source={id,name}`；`recordType=manual|file|device`。时间使用带时区的ISO测量时间，ingestedAt/updatedAt为毫秒；测量日按其原时区日期前缀，不按导入日归类。区间、分期、外部ID没有时为null；不保存密码、Token或原始个人文件。
- 指标：steps_total（当日累计，步）、steps_hourly（明确单小时区间，步）、heart_rate/resting_heart_rate（bpm）、sleep（分钟）、active_minutes（分钟）、distance（km）、energy（kcal）、spo2（%）、stress（明确百分制）。睡眠可带起止与真实deep/light/rem/awake分钟；缺失不推测。
- 首页和健康页共用摘要函数：步数取所选日最新累计值，不累加多次快照；心率取截至所选日最近有效记录并显示时间；睡眠取截至所选日最近完整记录。每项显示来源，旧日期明确标注；不把不同来源加在一起。小时趋势只画同一来源真实小时区间；近7日缺失为缺失，不填假0。
- 手动创建/原ID编辑/确认删除；导入先校验、显示类型/数量/来源/重复及冲突，确认后重新读快照；同ID不同内容停止，来源+外部ID或指标/测量时间/区间相同但内容冲突也停止，不自动覆盖更完整内容。完全相同则跳过，文件最多5MiB/10000条，超限拒绝整份而非截断。
- 导出保留原ID/来源/测量及导入时间；恢复不把原设备记录伪装成新同步。lastImportAt只在真实确认新增导入后记录。设备始终“未连接/等待同步”，文件恢复只显示“已导入”，不显示“设备已同步”。
- DemoProvider仅显式预览、内存数据，清楚标记合成，不进入首页真实摘要/存储/JSON。Manual与FileProvider归一化后经同一保存边界；DeviceProvider仅返回不支持及能力说明，不发起蓝牙、登录或网络请求。
- 隐私：默认本地、导出明确提醒含健康记录；只由用户下载，文件名不含具体指标值。Git忽略健康备份文件名。无医疗诊断/健康评分、云上传或自动同步。

## B 的实施细则

- v10是在原v9完整对象上追加`health`；不改其旧字段，不添加v9不能识别的内容。完整v10上限45MiB；健康独立文件5MiB，存储容量校验预留1KiB文件封装空间、导出紧凑JSON，避免生成自身无法读回的文件。
- 原媒体解码器保留，用app适配将v10媒体部分按v9规则严格解码；原跨存储保存日志/回滚继续复用，健康键参与v10快照与确认合并。旧版备份缺少health时不读取/写入该键。
- 测量身份为来源+指标+外部ID，或来源+指标+测量时刻+起止区间；不同指标可共享同一原始行引用。分期不同不自动覆盖。小时步数归区间开始日，支持23:00至次日00:00；睡眠按醒来/测量日，均保留原时区。
- 编辑仅用于手动类型，保留原ID/首次记录时间/原时区；导入的设备/文件原始测量只读，可明确删除或另建手动记录。演示来源仅内存预览，不能通过健康JSON持久保存。
